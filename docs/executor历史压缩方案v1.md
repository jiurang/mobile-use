# Executor 局部历史压缩 · 方案 v1

> 整理日期：2026-10-26
> 对象：`minitap/mobile_use/agents/executor/`（局部历史 = `state.executor_messages`）
> 数据来源：mobile-manager 真机归档（PG `mobilemanager`），execution 872 / 874 / 876 / 880 / 881
> 取数脚本：`mobile-manager/scripts/probe_executor_history_growth.py`（只读，可重跑）

---

## 0. 一句话结论

Executor 的局部历史是**唯一随步数线性增长**的一段，末轮占整个 executor prompt 的 **54%~67%**
（execution 880：60,272/110,992 = 54.3%；execution 876：97,846/147,153 = 66.5%），
而 executor 又占了全任务 **99%** 的输入 token。

**主推方案：在发给 LLM 的那份副本上做「位置无关的逐条压缩」**（三档预算 + 失败事实逐字保留）。
实测（真机归档回放）局部历史字节降到 **41%~72%**，全程 prompt 字节降 **13%~34%**，
**前缀缓存不击穿**（已发出的字节永不改变）。

**有界窗口（只留最近 K 轮）不作为第一方案**：它把 prompt 压到 17% 看着更省，但每轮把整个窗口
按满价重算 ⇒ 缓存命中率从 ~86% 掉到 ~33%，且模型会失去跨步上下文（失败事实恰恰住在历史里）。
它只适合当**第二阶段的上界护栏**，且必须先 A/B。

## 1. 现状事实（全部来自真机归档，不是估计）

### 1.1 executor 是唯一的大头

`execution_events` 里 `kind='usage'` 按 agent 拆账：

| execution | 任务 | agent | 次数 | input | 其中缓存命中 | 输出 | 思考 | 平均耗时 | 平均 input/次 |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|
| 880 | 淘宝红包签到（FAILED） | **executor** | 186 | **4,052,117** | 3,491,816 | 134,154 | 102,886 | 8.1 s | 21,786 |
| | | 其余全部 agent | 12 | 41,622 | 6,049 | 4,227 | 2,180 | — | — |
| 876 | 抖音极速版-刷视频 | **executor** | 139 | **3,480,599** | 3,134,950 | 270,222 | 241,239 | 12.0 s | 25,040 |
| | | 其余全部 agent | 3 | 16,287 | 686 | 3,175 | 2,147 | — | — |

⇒ **executor 占全任务输入 token 的 99.0%**（880）/ 99.5%（876）。
⇒ executor 的缓存命中率 **86.2%**（880）——历史是稳定前缀，所以它在账上主要是**缓存读**。

### 1.2 局部历史是唯一 O(n) 段

execution 880 末轮（call 198）：**110,992 字符 / 461 条消息**，其中局部历史 60,272 字符（**54.3%**）。

| call | 总字符 | 消息数 | 局部历史 | 占 prompt |
|---:|---:|---:|---:|---:|
| 3 | 11,635 | 4 | 0 | 0.0% |
| 29 | 22,959 | 52 | 8,456 | 36.8% |
| 101 | 50,660 | 179 | 21,654 | 42.7% |
| 148 | 77,991 | 317 | 42,124 | 54.0% |
| 198 | 110,992 | 461 | 60,272 | **54.3%** |

增长是**线性的**：约 **3 条消息 / 步**（assistant + tool + Contextor 事实行）、**约 490 字符 / 步**。

**换子目标会归零**（`agents/cortex/cortex.py:707` 清空 `executor_messages`）⇒
一个子目标内跑 50 步，历史就有 ~150 条消息 / ~25k 字符。

### 1.3 局部历史里三类内容的占比（execution 880 末轮）

| 内容 | 条数 | 字符 | 占局部历史 | 能不能压 |
|---|---:|---:|---:|---|
| assistant（模型的思考 + 动作） | 152 | 31,722 | **52.6%** | 能（散文） |
| tool（工具结果） | 151 | 11,809 | 19.6% | 部分（失败类不能压） |
| user（Contextor 的「上一步的结果」） | 153 | 16,741 | **27.8%** | 能（截断那坨 OCR） |

尾部每轮变的块（失败清单 306 / 设备状态 66 / 元素表 3,133）**不是历史**，不参与压缩。

### 1.4 字节具体花在哪（真实样本）

**① 模型的思考 —— 每步重新列举整张任务清单**（中位 225 字符，最长 484）：

```
"滑动后列表已上移，现在能完整看到任务列表（包括之前被遮挡的第一个任务）。当前可见任务有：
 好物沉浸看(0/4)浏览30秒最高得+500、去支付宝蚂蚁庄园逛(0/1)完成任务最高得+80、
 搜索你喜欢的宝贝(1/2)浏览15秒最高得+1898、一键分享赚元宝(点击分享即可得+360)……"
```

⇒ 同一张清单，模型在 150 步里重列了 150 遍。这是**最大的单笔浪费**。

**② 工具结果 —— 多数已经很短，但成功结果带机器载荷**（中位 65，最长 625）：

```
"Tap on element with resource_id='com.ss.android.article.news:id/bt5' -> coordinates (650, 856)
 was successful. ctx:{"t":"全面从严治党 为什么要一","i":8,"w":["科技榜","汽车榜",...]}"
```

`ctx:{...}` 是**机器 JSON**（当时的屏幕文本快照），不是给模型看的散文。

**③ Contextor 的事实行 —— 「屏幕上新出现了」后面是一坨 OCR 原文**（中位 103，最长 612）：

```
"[上一步的结果] \"同意\" btn_privacy_agree 这一步失败了；前台应用没变（还是 …）；
 屏幕上新出现了：账号在其他设备登录、你的支付宝账号于10-26 09:02在设备\"一加 Ace 5\"上登录。
 如果这不是你的操作，你的登录密码已泄露，请尽快修改、你的支付宝账号于…登录。如果这不是你的操作,、
 请尽快修改、好的 等 8 条"
```

⇒ 失败事实 + 前台 app 是**要留的**；后面那坨 OCR 原文是**噪音**。

### 1.5 计价事实

MiniMax-M3.1-Flash（execution 880 用的渠道）官方定价：
**输入 $0.15 / M tokens，输出 $0.60 / M，缓存读 $0.015 / M**（= 缓存读是满价的 **1/10**）
（国内口径：输入 1 元 / 输出 4 元 / 缓存读取 0.1 元每百万 token）

⇒ **历史在账上主要是「缓存读」**。压缩省的是缓存读 token（便宜）+ 延迟 + 上下文占用，
不是满价 token。这个预期要先说清，别把「省了 30% 字节」当成「省了 30% 钱」。

按这个单价算 execution 880 的 executor：

| | 现状 | 逐条压缩后（prompt 字节 -13.4%） | 变化 |
|---|---:|---:|---:|
| 输入侧 | $136.4 | $118.1 | **-13.4%** |
| 输出侧（输出+思考） | $142.2 | $142.2 | 0 |
| **executor 合计** | **$278.6** | **$260.3** | **-6.6%** |

execution 876 同口径：executor 合计 $405.6 → $372.5（**-8.2%**）。

⇒ **输入侧降 13%~34%，但输出侧（思考）占一半以上 ⇒ 整任务账单只降 7%~8%。**
真正的收益在**上下文占用**（末轮 46k token → 约 25k token）和**质量**（需 A/B 验证）。

## 2. 三条硬约束

1. **位置无关**：第 i 条的渲染**只依赖第 i 条自己** ⇒ 已发出的字节永不改变 ⇒ 前缀缓存不击穿。
   （与 `utils/thoughts_compaction.py` 同一个性质、同一套论证 —— 那里实测滑窗命中率 47.2%、
   位置无关压缩 91.1%。）
2. **事实不能压**：失败事实**逐字保留**。判定复用 `thoughts_compaction` 同一套正则口径。
3. **只改副本不改 state**：`state.executor_messages` 是 Reporter 的事实来源
   （`agents/reporter/reporter.py` 逐字搬运），压缩只作用于**发给 LLM 的那份**，
   和现有 `truncate_local_history`（L5）同一个位置、同一条纪律。

---

## 3. 三条压缩规则

### R1 · assistant 的 `agent_thought` → 首句 … 末句

- **动什么**：`tool_calls[].args["agent_thought"]` 的**文本**。
- **不动什么**：`actions`（动作）、`tool_call_id`、`name`、消息结构 —— 一个字节都不动。
- **为什么留首末句**：首句 = 结论（「列表已滚到中部」），末句 = 策略/理由（「我先向下滚动看完剩余任务」）。
  中间是任务清单的复述，对下一轮决策价值最低。
- **为什么不能整条丢**：历史是模型下一轮**模仿的对象**
  （`prompt.py::rewrite_history_tool_calls` 的实测结论：历史里带设备工具名，模型就跟着喊错工具名）。
  字段和形状必须留着，只缩短文本。

### R2 · tool 结果 → 成功：首句 + 丢 `ctx:{...}`；失败：逐字保留

- **失败判定**：内容正则（`fail|error|no element found|…`），与 `thoughts_compaction` 同一套口径。
  失败结果**一个字都不改** —— 模型要靠它判断「为什么失败、换哪」。
- **成功结果**：留结论句；`ctx:{...}` 是机器 JSON 载荷，**丢**（或整条截尾）。
- **载荷类工具豁免**：`read_note` / `list_notes` / `focus_and_input_text` / `focus_and_clear_text`
  的结果**不是冗长回显**，截掉就是丢模型要的东西本身 —— 与现有 L5 的 `_PAYLOAD_TOOLS` 同一套豁免。

### R3 · Contextor 的「上一步的结果」→ 保住事实，截断 OCR 噪音

- **留**：`… 这一步失败了`（失败事实）、`前台应用变成了/没变`（客观事实）。
- **截**：`屏幕上新出现了：<一坨 OCR 原文>` → 前若干字符 + `（共 N 条）`。
- **为什么**：`executor.md` 明确告诉模型「你的历史里有『上一步的结果』…… 先读它」，
  但它要的是**有没有变、变了哪个目标**，不是那坨屏幕原文。

## 4. 落点

| 项 | 位置 |
|---|---|
| 新模块 | `minitap/mobile_use/utils/executor_history_compaction.py`（与 `thoughts_compaction.py` 同构） |
| 接入点 | `agents/executor/prompt.py::build_executor_messages` |
| 开关 | `PerceptionConfig.executor_history_compaction: bool = True`（与 `thoughts_compaction` 同款回退开关） |
| 预算常量 | 先硬编码在模块里；验收后再决定要不要外露成配置 |
| 单测 | `tests/mobile_use/test_executor_history_compaction.py` |

### 接入顺序（**有理由，不能换**）

```
build_executor_messages:
    messages.extend(rewrite_history_tool_calls(truncate_local_history(local_messages)))
                        ↑ 改成：
    messages.extend(rewrite_history_tool_calls(compress_history(truncate_local_history(local_messages))))
```

1. **先截断（L5）**：它靠**原工具名**判载荷豁免（`_PAYLOAD_TOOLS`），改写之后名字变成
   `ExecutorOutput`，豁免就失效了。
2. **再压缩**：压缩需要知道工具名（判载荷豁免）→ 必须在改写**之前**。
   但 assistant 的 `agent_thought` 在**两种形状里都在 `args["agent_thought"]`**，
   压缩完再改写，压缩后的文本会被原样带过去 ⇒ 不冲突。
3. **最后改写 tool_calls 名**（现有逻辑，不动）。

### 三个必须处理的实现细节

- **多模态内容不能整体 `str()`**：带图的消息，其 content 是 `[文字块, 图片块]`。
  压缩文本时用 `utils/message_content.with_text_replaced`（图片块原样保留），
  和 `truncate_local_history` 完全一样的处理。
  （⚠️ 2026-10-27：截图工具已整条移除，现在实际带图的工具结果没有了 ——
  但这条处理**保留**：它防的是「任何多模态内容」，不只是截图。）
- **`tool_call_id` 一个都不能动**：它是 OpenAI 兼容端点配对 AIMessage / ToolMessage 的依据，
  动了会 400（历史 bug 3，同一类）。
- **不能拆散配对**：本方案**不丢弃任何消息**（只改内容），所以不存在「孤儿 tool_call」。
  如果以后要做有界窗口，**必须成对丢弃**（assistant + 它的 tool 结果一起丢）。

## 5. 为什么第一版不做「有界窗口」

用同一批真机数据回放模拟（留最近 20 条历史）：

| | 现状 | 逐条压缩（位置无关） | 有界窗口（位置相关） |
|---|---:|---:|---:|
| 全程 prompt 字节 | 9,829,916 | 8,507,939（-13.4%） | 1,671,726（**-83%**） |
| 局部历史字节 | 4,705,963 | 3,390,583（-28%） | ~（只剩最近 20 条） |
| 缓存命中率 | ~86% | ~86%（**不变**） | **~33%** |
| 满价等效（缓存读按 1/10） | 5,099,457 | — | 1,182,571（-76.8%） |

窗口版**账单上更省**（-76.8% 满价等效）。但它有两个硬代价：

1. **缓存命中率掉到 33%**：每轮整窗按满价重算。省下的钱是真的，但**没有省下时间**——
   prefill 的字节数没少（甚至因为重复写缓存而多写）。
2. **质量风险**：失败事实住在历史里。丢掉 20 轮之前的历史，模型就不知道「这条路走不通」，
   而这正是「不要在同一个目标上死磕」的唯一依据。execution 880 那个
   「去头条刷热点领现金(0/1)」卡 70 步的案例，正是历史太长 + 没有 failed 出口造成的；
   再把历史砍短，可能让它**更快地**原地打转。

⇒ **第一版只做逐条压缩**。有界窗口留作第二阶段的「上界护栏」，前提是：
① 逐条压缩后历史仍然超长（例如单子目标 > 100 步）；② 先 A/B 证明质量不掉。

## 6. 验收方法

### 6.1 单元测试（`tests/mobile_use/test_executor_history_compaction.py`）

| 断言 | 为什么 |
|---|---|
| 位置无关：同一条历史项在「更长/更短」的上下文里渲染结果**逐字节相同** | 缓存安全的前提 |
| 已发出字节不变：`render(h[:k])` 是 `render(h[:k+1])` 的字节前缀 | 同上 |
| 失败事实逐字保留 | 「事实不能压」 |
| `tool_call_id` / `name` / 消息结构不变 | 端点配对 |
| 图片块不丢 | 带图的多模态工具结果（截图工具已于 2026-10-27 移除） |
| 载荷类工具豁免 | `read_note` 等 |
| `enabled=False` 时逐字节等于原文 | 回退开关 |

### 6.2 离线回放（不用真机）

`mobile-manager/scripts/probe_executor_history_growth.py --simulate`
→ 把捕获的真实 prompt 喂进新渲染函数，比对字节数与保留内容。

### 6.3 缓存断点复检

`mobile-manager/scripts/probe_prompt_cache_breakpoint.py 880 --agent executor`
→ 字符级 LCP 必须仍然只差「尾部块 + 新增那一轮」；**压缩后 LCP 不能变小**。

### 6.4 真机 A/B（必须做）

同一任务、同一渠道、同一手机，开/关各跑一次，比：

- `usage` 事件的三列：输入 / 缓存命中 / 输出（**别只看输入**，缓存命中率也要看）
- **步数与完成率**（质量口径，不是成本口径）
- 平均耗时

脚本：`mobile-manager/scripts/compare_exec_cache.py`（缓存命中率对照）、
`compare_exec_per_agent_cache.py`（按 agent 拆）。

## 7. 风险清单

| 风险 | 处置 |
|---|---|
| 压掉关键信息 → 模型跑偏 | 失败事实逐字保留；thought 保留首末句；A/B 看**步数与完成率** |
| 动了 tool_calls 结构 → 端点 400 | 只改 `args["agent_thought"]` 的文本；id / name / 结构一个字节都不动 |
| 与 L5 截断叠加 | 压缩在截断**之后**，两者命中条件不同，互不干扰 |
| 压缩后模型不再产出思考 | 字段与形状保留，只缩短文本；A/B 看输出 token 是否下降异常 |
| 图片消息被压成 base64 噪声 | 用 `with_text_replaced`，图片块原样保留 |
| 只在中文任务上验证过 | 预算用 token 估算（复用 `estimate_tokens`），中英文同一套 |

## 8. 预期收益（保守口径）

| 指标 | 变化 | 证据 |
|---|---|---|
| executor 局部历史字节 | **-28% ~ -59%** | 真机归档回放（880 / 876） |
| executor prompt 字节 | **-13% ~ -34%** | 同上 |
| 末轮 prompt 体积 | 880：111k → 94k 字符（46k → 39k token）<br>876：147k → 90k 字符（61k → 37k token） | 同上 |
| executor 输入侧账单 | **-13% ~ -34%** | 按 M3.1-Flash 官方单价算 |
| **整任务账单** | **-7% ~ -8%** | 输出侧（思考）占一半以上，压不动 |
| 前缀缓存命中率 | **不变**（位置无关） | 设计保证 + 断点探针复检 |
| 上下文占用 | 降 16%~39% | 对 MiniMax（1M 窗口）无风险；对 GLM / DeepSeek 等小窗口渠道**是真实的崩盘风险** |
| 任务质量 | **待 A/B 验证** | 不能先下结论 |

## 9. 后续可做（不在本方案范围）

- **跨步去重**（第二阶段）：模型每步重列同一张任务清单。
  实测 execution 876 有 **1,455 条思考与前面某条高度重复**，占思考总量 **15.6%** ——
  逐条压缩压不掉这部分。
  **缓存安全性**：渲染规则若是「第 i 条若与第 j 条重复 ⇒ 渲染成『（与第 j 步重复）』」，
  则第 j 条自己的渲染不变 ⇒ 已发字节不变 ⇒ 仍然位置无关。
- **有界窗口**（第三阶段）：只作为「单子目标步数失控」时的上界护栏，必须成对丢弃
  （assistant + 其 tool 结果），且必须先 A/B。
