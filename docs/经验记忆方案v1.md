# 经验记忆方案 v1

面向 mobile-use / mobile-manager 这套手机自动化系统。目标是让系统把**跑过的经验留下来**，下一次做同类任务时，Supervisor（Cortex）和执行者（Executor）在动手之前就能看到这些经验。

## 要解决什么

一个具体场景：某个 app 的「签到入口」在首页左上角，模型每次都要自己试五到八步才找对；或者某个控件必须长按才响应，模型每次都先点一下、被弹窗挡住、再改。这些都是能复用的判断，但现在每次运行都从零开始。

系统里已经有三种「知道的东西」，都覆盖不到这件事：

| 已有 | 存在哪 | 谁写 | 覆盖什么 | 缺什么 |
|---|---|---|---|---|
| 用户画像 persona | manager PG | 人工 | 「像谁」 | 和 app 无关 |
| 应用提示词 app_prompt | manager PG | 人工 | 「在这个 app 干什么」 | 是模板，不是经验 |
| 脚本库 macro | manager PG | 从一次成功执行编译 | 「怎么做一遍」 | 改版即失效；不回答「哪里会坏」 |
| 笔记 scratchpad | 运行内 state | Executor 工具 | 跨子目标传话 | 活不过一场运行，2026-10-23 停用 |

缺的是第四种：跨任务的经验条目，一句话说明「这个 app 的这件事该怎么走、哪里是坑、什么条件下会坏」。

和脚本库的区别是实在的。脚本库存的是一串可回放的动作，app 改版后大概率失效——真机实测快手在 4 小时内把同一个搜索入口从 `right_tv` 改成了 `thanos_home_top_search`；而「签到入口在首页左上角」这类判断，改版后多半还成立。两者互补，不该合成一个东西。

## 一条记忆长什么样

按四类存，类型决定它怎么被验证：

| 类型 | 说的是什么 | 例子 |
|---|---|---|
| 事实 | 屏幕上确凿的东西 | 「签到弹窗里的按钮文案是「立即领取」，不是「领取」」 |
| 坑 | 这么做会失败 | 「点首页的「任务」入口进不去签到，那个入口是广告」 |
| 路径 | 正确的走法 | 「签到在首页左上角头像下方，点「签到」卡片，不是右上角」 |
| 结论 | 判断和它的前提 | 「这个 app 的搜索框在顶部通栏，不是搜索图标」 |

字段：

| 字段 | 作用 |
|---|---|
| kind | 上面四类之一 |
| title | 一行短描述，同时是检索关键词和模型看到的第一行，长度上限和脚本库候选摘要一致（160 字符） |
| detail | 正文 |
| evidence | 逐字证据：错误原文、屏幕读数、控件标识。从轨迹里抄，不改写 |
| insight | 模型写的解释和建议。可以压成首句…末句 |
| keywords | 检索用关键词，一般 3 到 8 个 |
| scope / app_package / device_serial | 作用域：整个 app、某台设备、还是全局 |
| importance | 1 到 3，写入时定一次，检索时不再算 |
| success_count / fail_count | 命中计票，见「验证」一节 |
| valid_from / valid_until | 有效期，过期不删除，只是不再优先用 |
| evidence_execution_id / evidence_event_ids | 溯源指回那次执行，能让人核对「这条是怎么来的」 |
| enabled | 人工开关，误写的经验可以一键停用 |

「事实逐字、散文可压」这条老规矩在这里落成两个字段：`evidence` 逐字，`insight` 可压。屏幕上的字和报错原文属于事实，压了模型就没法判断「为什么失败」；模型自己的解释属于散文，压掉中间铺陈保留结论即可。

## 谁写，谁读

写，按可靠性从高到低有三条路。

**离线提炼（第一版就做）**。任务结束后，manager 侧跑一个提炼器，从 `llm_prompts` 里读这次执行的完整轨迹——每次模型调用的请求和回答都原样存在这张表里——交给模型抽经验。

放这里有三个理由：结果是否达成是代码判的（Reporter 的 `determine_outcome` 不经模型），可靠；轨迹完整；不占运行时间，且提炼提示词改好了可以重跑历史执行。代价是每次执行多一次模型调用，但发生在任务结束之后，不影响用户等待。

**运行时写（第二版可选）**。让 Executor 在执行中自己写。

代价要说清楚：Executor 一轮只执行一个动作（元素编号只在那一屏上成立），写一条记忆要占掉一整个 Executor 回合，而 Executor 占全任务 99% 的输入 token，是最贵的一环。而且模型自述不可靠——它说「我学到了 X」不代表 X 对。所以这一路只允许它写原始事实（屏幕读数、控件文案），不允许写结论，结论交给离线提炼器或人工。

**人工写**。manager-web 上直接编辑，和脚本库、应用提示词放在同一个位置。

读，路径是：

1. 任务开始时按 app 检索一次，钉在 state 的 `memories` 字段里，**整场运行不变**。
2. Cortex 在决定下一个子目标时看它。
3. Executor 在每一步看它。
4. 要看正文，模型主动调 `read_memory(id)` 展开——和当年 `read_note` 一个套路，一次展开只花一次调用的钱。

## 注入位置就是缓存问题

这套系统的 provider 前缀缓存是整体键：请求体改一个字节，整条缓存作废，只剩一百多 token 的固定底噪。实测过两个反例：Cortex 下发新子目标时清空 Executor 局部历史，命中率从 41% 掉到 4.6%；`take_screenshot` 原地改写历史里那条带图的消息，命中率从 73% 掉到 41%。

所以记忆块放在哪一行，等于省多少 token。

Executor 的提示词顺序现在是：系统提示词、任务开始时间、目标陈述、局部历史、失败清单、设备状态、屏幕元素表。记忆块放在**任务开始时间之后、目标陈述之前**。

理由是它整场运行不变，属于「恒定」那一档。项目里的排序原则是按首次变化的时刻从早到晚排：恒定、只追加、每轮变。放进恒定档，它在整场运行里都在缓存的前缀里，一分钱不额外花。如果放进「每轮变」那一段（元素表附近），每一步都要满价重算——按 160 字符一条、五条一轮算，一个上百步的任务要多付几万 token。

Cortex 那边同理，放在「设备与目标」之后、「thoughts」之前。

还有两条硬规矩：

- **本次运行写的东西，本次不生效。** 检索结果在任务开始时钉住就再也不变，运行中产生的新经验留到下一次任务。否则记忆块会在运行中途变，前面所有字节重算。
- **渲染必须逐字节稳定。** 块里不插时间戳、不写「今天」「第 N 条」、排序按 id 排死。否则同样的输入两次渲染出不同字节，缓存就没了。

## 写：落库、判重、准入

提炼器拿到一条候选经验后，按这个顺序处理：

1. **准入**。「路径」和「结论」两类只在这次执行判定为达成时才产出——半路失败总结出来的路多半是错的。「坑」这一类必须有逐字失败证据，没有证据的坑不入库。「事实」类要求能指回具体的屏幕读数或控件标识。
2. **判重**。先按 app、关键词和标题做一次相似检索，把最像的几条拉出来，判断是「新经验」还是「同一条经验的又一次印证」。判重只加计数，不覆盖。
3. **落库**。追加写，不改旧条目。带证据指针、有效期和写入时的重要性分。
4. **冲突不覆盖**。两条经验互相矛盾时，带时间戳多版本并存，检索时优先「没失效、命中成功率高」的那条。

不覆盖是有道理的：手机 app 改版后，旧经验误导的危害远大于旧经验丢失。

## 验证：命中计票

一条经验对不对，最终裁判是**下一次用它的时候结果如何**。这是唯一不需要额外模型调用的验证机制。

- 任务结束时，这次注入过的每条经验记一票：相关子目标达成，success_count 加一；相关子目标失败，fail_count 加一。
- 这个信号是弱的：子目标成功不等于这条经验起了作用，失败也不一定是它的错。所以它只用来慢慢调排序，**不做因果判断**。
- 连续失败到 3 次，自动降权到最低优先级；再多就标记为过期，检索时不再优先给。带控件标识的经验（`resource_id` 之类）在界面指纹变了之后也按同样的方式处理。

人工审核始终是最终一道闸：manager-web 上能看、能改、能禁用，每条都带「从哪次执行来的」。

## 会遇到的问题和对策

| 问题 | 对策 | 依据 |
|---|---|---|
| 模型写的经验是错的 | 达成才产出路径和结论；坑必须带逐字证据；结果由后续命中计票慢慢纠正；人工可禁用 | Mobile-Agent-v3 的 Notetaker 只在成功时触发 |
| app 改版后经验过时 | 有效期 + 命中失败自动降权 + 界面指纹变化即降级；旧条目不删 | Graphiti 的事实失效语义 |
| 经验互相矛盾 | 不覆盖，带时间戳多版本并存，检索时排序消歧 | Mem0 的 ADD-only 与时间感知排序 |
| 经验库无限膨胀 | 按 app 分区，检索只取五条，上限固定，定期归档 | Reflexion 的容量上限思路 |
| 撑爆上下文、击穿缓存 | 注入位置放在恒定段；每条一行 160 字符；本次写入本次不生效；渲染逐字节稳定 | 本项目已实测的缓存行为 |
| 和脚本库功能重叠 | 边界写死：能回放的动作序列归脚本库，判不了「怎么走通」的归经验；同一件事两边都写时以脚本库为准 | Voyager 的技能库就是程序性记忆 |
| 隐私：屏幕内容是用户数据 | 跨任务只留结构性知识；验证码、订单号、身份证、手机号不落库，原值用占位符代替 | AWM 的「抽象掉实例特有值」 |
| 写得太多，库变噪 | 提炼器只收达成轨迹；每条经验必须能指回一次执行 | ExpeL 的两段式：留档后再抽 |
| 经验把模型带偏 | 提示词里写清：经验是提示不是指令；和当前屏幕矛盾时以屏幕为准 | 经验是二手信息，屏幕是一手信息 |
| 没人知道这功能有没有用 | 三个指标：注入条数与展开条数、带经验完成的子目标比例、经验条目的去重率与失效率 | 没有度量就没法判断 |
| 检索结果不稳定导致缓存反复失效 | 任务开始时检索一次并钉住，全程不再检索 | 本项目「已发字节不许改」的纪律 |

## 开源项目是怎么做的

| 项目 | 机制 | 我们借鉴什么 |
|---|---|---|
| [Letta / MemGPT](https://www.letta.com/blog/agent-memory) | 常驻 core memory + 工具化检索的 archival memory；[sleep-time compute](https://www.letta.com/blog/sleep-time-compute) 在任务之外异步重构记忆 | 两层结构；离线整理放在任务结束之后做 |
| [Mem0](https://github.com/mem0ai/mem0)（[论文](https://arxiv.org/abs/2504.19413)） | 抽取后判重再落库；[新版](https://docs.mem0.ai) 改成只追加、靠时间排序消歧 | 写入时判重；矛盾不覆盖 |
| [Zep / Graphiti](https://github.com/getzep/graphiti) | 事实边带 valid_at / invalid_at / expired_at，旧事实失效不删 | 经验条目的有效期与失效语义 |
| [LangMem](https://github.com/langchain-ai/langmem) | hot path（运行时自己写）与 background（事后反思抽取）分开 | 冷热两条写入路径的切分 |
| [Generative Agents](https://arxiv.org/abs/2304.03442) | 检索打分 = 新近度 × 重要性 × 相关度；重要性在写入时打一次 | 五条候选的打分配方；写入时定重要性 |
| [Reflexion](https://arxiv.org/abs/2303.11366) | 失败后把反馈放大成一句可执行的经验，存进有上限的缓冲区 | 失败经验写成「下次别这样」；容量上限是天然的刹车 |
| [Voyager](https://arxiv.org/abs/2305.16291) | 技能用一句描述做索引，检索取 top-5；验证成功才入库 | 描述即索引；成功准入闸门 |
| [ExpeL](https://arxiv.org/abs/2308.10144) | 先留原始轨迹，再离线抽跨任务的通用结论 | 原始事实留档、事后抽经验的两段式 |
| [Agent Workflow Memory](https://arxiv.org/abs/2409.07429) | 从轨迹里诱导出反复出现的子流程，刻意抽象掉实例特有值 | 经验写成「在 {app} 打开 {功能} 的路径是…」，不写具体坐标 |
| [Mobile-Agent-v3](https://arxiv.org/abs/2508.15144) | Manager / Worker / Reflector / Notetaker 四角色；Notetaker 只在成功时抽易失事实 | 只在成功时写；事实来源是判定器不是模型自述 |
| [Claude Agent Skills](https://code.claude.com/docs/en/skills) | 三层装载：描述常驻、正文按需读、附件用到才读 | 只有一行摘要常驻上下文，正文由模型自己决定展开 |
| [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 目标是「能产生目标行为的最小高信号 token 集合」；笔记写在上下文之外，要用再拉 | 经验库放外面，检索时才进上下文 |

对我们的取舍是四条：记忆分两层且变动内容全部排在后面；写入走后置提炼加成功准入，不在 Executor 热路径写；每条经验固定字段并能指回产生它的那次执行；检索先按 app 和类型过滤，再打分取五条。

顺带说一句：manager 已经在用 PostgreSQL，需要向量检索时 [Mem0 的开源实现](https://docs.mem0.ai) 把 pgvector 列在受支持的向量库里，同一个实例就能用，不必另起一套。第一版不需要向量——五条候选的规模上，关键词加元数据过滤加简单打分在 Java 里就够了。

## 分阶段落地

**第一版**：新表 `memories`；manager 侧 `/api/memories` 四个端点（检索、正文、写入、命中计票）；离线提炼器从 `llm_prompts` 抽经验；mobile-use 侧加 `memory/store.py` 客户端和 `state.memories`，Cortex 与 Executor 各注入一块；manager-web 上能看能禁用。

**第二版**：Executor 运行时写原始事实（默认关）；按子目标关键词二次检索；经验与失败事实合并成一条带证据的「避坑清单」。

**第三版**：命中率更好的排序（pgvector 或更强的重排）；把反复验证有效的路径编译成脚本库条目。

## 明确不做的事

- 不做「记忆自动改写提示词」这种玩法：改提示词就是改前缀，等于每次全量重算。
- 不让记忆代替证据：Executor 判定达成仍然只看当前屏幕，经验只影响「怎么走」。
- 不在运行中把新写入的记忆插进当前上下文。
- 不引入独立向量数据库作为第一版的前提。
- 不把跨任务经验写成用户数据：验证码、订单号这类值不落库。
